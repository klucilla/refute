# WP3 addendum: data sources, evaluated populations and readers

Addendum to [wp3-acceptance.md](wp3-acceptance.md) (and, for one change in the core, to
[wp2-acceptance.md](wp2-acceptance.md)). Committed **before** its tests and code (plan
section 11). Line numbers refer to the files at commit 4b06b3d.

## 0. Why, and who decided

Preparing the runs of the development papers and the inventories of the main sample
(2026-10-18) showed three gaps of the ML pack, all on the side of Refute:

- **A. Data the repository generates.** `MlTestPlan.datasets` requires at least one
  downloadable artifact with URL, hash and size (`src/refute/packs/ml/schema.py:243` and
  `:293`), and `data_present` is a required gate of the core (`src/refute/core/paper.py:40`,
  checked at `:331`). A paper whose data are generated by its own code (2304.14390: toy
  targets in `src/toy/distributions.py`; 2407.20299: Procgen rollouts) cannot be written
  as a claim.
- **B. Populations made by the code.** `Metric.split` must be a split of the downloaded
  file and `metric.n_examples` its declared size (`schema.py:340-348`). Several papers
  evaluate a population their code derives from the file: 2309.15704 (the OOD and test
  sets cut along the first principal component, `datasets.py` of its repository),
  2302.12465 (a 7:1:2 split of one edge type), 2305.19518 (a validation set cut from the
  training file).
- **C. Files the readers cannot count.** `readers.py` counts `npz`, `npy`, `csv`, `tsv`,
  `jsonl`, `parquet` and those formats inside a zip. The sample needs the CIFAR "python"
  archives (a tar.gz of pickled batches), Excel files (UCI), whitespace-separated text and
  ARFF (UCI, OpenML), and a DGL graph file (2302.12465). Without a count, `data_present`
  is `INCONCLUSIVE` (`integration.py:462-470`) and so is the claim (`paper.py:341-344`).

The design was decided by the agent with Codex on 2026-10-18 (thread
`01a14f0b-0899-7253-93cd-6bef1ddaa79f`, read only), under the working mode of the
maintainer (CLAUDE.md, "Working mode (v0.3)"). The maintainer was told the same day. What
Codex recommended and this document keeps:

- a typed source per dataset, never a fictitious URL or hash;
- the evaluated population separate from the origin of the data;
- `data_present` may be **not applicable** only for data the repository generates, with a
  reason fixed before the lock, and never as a `PASS` or as an artificial coverage;
- any other check that applies and cannot be run stays `INCONCLUSIVE`, never "not
  applicable";
- no generic unpickling in the orchestrator: formats that need a library or code run in
  the paper's own container, with a closed catalogue of readers written by Refute;
- a build that is not a Python environment (CMake) is a limitation of Refute, recorded as
  such (`INCONCLUSIVE`), not a new rung of the ladder.

Codex then reviewed this text before any test or code (thread
`01a14f21-3d1d-7393-b951-6960d2ab0e77`, 2 rounds): five objections and their
improvements (the integrity and order of `repository_file`, the start-up of the
container reader, the strict parser and the declared residual trust, the automatic
minimum coverage of the exempt gate, `other_splits` with the derived splits) are in the
text below; it closed with agreement.

## 1. Dataset origins (D-A1)

`test_plan.datasets` holds entries of three kinds, distinguished by `origin`:

| `origin` | Fields | What `data_present` checks |
|---|---|---|
| absent, or `downloaded` | as today: `name`, `url`, `reference`, `version`, `license`, `retrieved_utc`, `sha256`, `size_bytes`, `local_copy_allowed`, `splits`, `size_tolerance` | as today: the fetch result of the declared artifact and the count of every declared split |
| `repository_file` | `name`, `path` (relative, `/`, no `..`), `sha256`, `size_bytes`, `splits`, `size_tolerance` | the file at `path` in the repository at `repository.commit`: its SHA-256 and size equal the declared ones, then the count of every declared split. A different hash or size is `FAIL` with no artifact cause (the claim then says `INCONCLUSIVE`, as for a wrong count) |
| `generated` | `name`, `generator` (one or more citations `{file, lines, role}` of the code that generates the data, at the pinned commit), `configuration` (text: the arguments and configuration files that fix the generation), `inputs` (names of `weights` entries the generation uses, possibly empty), `splits` | nothing: the gate is not applicable (section 3) |

- **Compatibility.** `origin` absent means `downloaded`, and the resolution writes nothing
  new for such an entry, so the resolved hash of every existing claim is unchanged.
- `name` is unique across the list, whatever the origin. A `generated` entry lists every
  name of `inputs` in `test_plan.weights`; those weights are fetched and checked as any
  weights entry (the exemption of section 3 covers `data_present` only). **Until the
  production fetches, checks and mounts declared weights** (not done by the current
  version, for any weights entry), a claim file with weights is refused before anything
  runs, never run with its weights unchecked (added after the end-of-round review of
  2026-10-18).
- **What `generated` means.** Data the repository's code creates from nothing but its
  configuration, its seeds and the declared `inputs`. Loading, transforming, filtering or
  splitting an existing file never makes it `generated`: that file is `downloaded` or
  `repository_file`, and the population the code cuts from it is a derived split
  (section 2).
- `repository_file` data are the repository's own: their licence is the repository's
  (or, for data the repository redistributes, the original source's, by C2 of the main
  protocol); the claim records it in the protocol's triage, not here.
- **`repository_file`, integrity and order.** `path` must name a regular file inside the
  clone: the path resolved without following links stays under the clone's root, and no
  component of it is a symbolic link; anything else gives no file (`data_present`
  `INCONCLUSIVE`). The order is fixed: checkout, then a copy of the file's bytes into
  Refute's cache outside the clone, where its SHA-256 and size are checked, before any
  build or code of the repository runs; then the build; then the count; then the runs.
  The count and every run read that same verified copy, mounted read only at the
  declared place (as the fetched datasets are, `production.py:309-366`), so a build or a
  run cannot change what was checked.

## 2. Evaluated populations (D-A2)

A dataset entry declares the populations a claim may evaluate:

- **`splits`** (every origin): for `downloaded` and `repository_file`, the parts of the
  file and how each is counted (`source`, section 4), as today; for `generated`, each
  split is `{expected_examples (≥ 1), unit, source}`, where `unit` names what one example
  is (`episode`, `sample`, `run`, ...) and `source` cites where the paper or the
  repository states the number (text).
- **`derived_splits`** (`downloaded` and `repository_file` only, optional): a map from a
  name to `{expected_examples (≥ 1), derived_from, rule, code}`:
  - `derived_from`: a non-empty list of **distinct** names of `splits` of the same entry;
  - `rule`: the rule as text (for example "the lowest and highest 25% of the rows along
    the first principal component");
  - `code`: citations `{file, lines, role}` of the code that derives it, at the pinned
    commit.

  A derived split name may not repeat a split name.

`metric.split` names a split or a derived split of the claim's dataset, and
`metric.n_examples` equals its `expected_examples` (as `schema.py` already requires for a
split). The coverage routes of `metric_extracted` compare their observed count with
`metric.n_examples` (W3.12a), unchanged.

`data_present` keeps checking the file's `splits` only, in this order: **every** declared
split of the file is counted and compared with its size first (`integration.py:473-483`,
unchanged), so a wrong count anywhere fails the gate whatever the claim's split; only then
is the coverage computed. Its coverage for a claim on a derived split is the sum of the
counts of `derived_from`, with the unit "examples of the source splits": a sum of the
declared parts, not a count of distinct examples (two overlapping file splits would be
counted twice; the claim names the splits the code reads). It is never
`expected_examples`.

**The routes that see labels.** `saved_predictions` and `hook` identify the split by its
labels (W3.12d); a derived split states its own `labels_sha256` in the claim like any
other split, and `split_identity.other_splits` must list **every** split and derived split
of the dataset except the claim's own (today only `splits`, `schema.py:1481`). Two
evaluable populations with the same sequence of labels cannot be told apart by these
routes, which then do not apply (as today). A derived split whose labels change with the
seed has no fixed `labels_sha256`; these routes cannot identify it and are
`INCONCLUSIVE`. The host attacks `leakage` and `trivial_baseline` read the labels and
examples of file splits only: on a derived split they are `INCONCLUSIVE` when they apply
(the claim may declare them not applicable with a reason, as any attack).

## 3. `data_present` not applicable for generated data (D-A3; WP2 change)

- **Core.** `aggregate_claim` (`src/refute/core/paper.py:265`) takes
  `not_applicable: Mapping[str, str]`, a gate name and its reason. Only `data_present`
  may be given (a closed tuple, `WAIVABLE_GATES`); any other name, a reason that is not
  text with content after `strip()`, a result for a gate declared not applicable, or a
  failure cause or a minimum coverage for it is a `ValueError` (input refused, no
  evidence dropped silently). These checks run with the other input checks, before any
  rule can return. Rule 1 of the verdict order skips a gate declared not applicable;
  every other rule is unchanged. `ClaimVerdict` carries the map in **every** verdict it
  returns, so the dossier and the report state it.
- **Pack.** The resolution writes `not_applicable: {data_present:
  generated_by_repository_code}` on every claim whose dataset is `generated`, and only
  then; a claim may not write it by hand. For such a claim the resolution writes no
  minimum coverage of `data_present` (`schema.py:1163` and `:1202` write one for every
  gate today), and a minimum given by hand for it is refused, never dropped. The gate is
  not computed and not recorded as a result. A claim whose dataset is `downloaded` or
  `repository_file` never has the map.
- **The link with the origin.** The core does not know the origin of the data. The pack
  checks the equivalence "`origin: generated` ⇔ `not_applicable` holds `data_present`"
  when it resolves the claim, when it runs it (`integration.py`, before the base
  checks), and when the dossier is verified and the verdicts recomputed; a difference is
  an error of the claim or of the dossier, never a verdict.
- **What still needs evidence.** `environment_build`, `run_completed` and
  `metric_extracted` stay required. `metric_extracted` needs its coverage route as today:
  with no observed count of the evaluated population (a printed count, saved predictions,
  sufficient statistics or the hook), it is `INCONCLUSIVE`, so the claim is. A count the
  configuration fixes is not an observed count.
- **The other checks.** Each attack keeps its own applicability, declared in the claim
  before the lock with its reason (`schema.py:613`). An attack that applies and has no
  data to read (for example `leakage` with no file splits) is `INCONCLUSIVE`, never not
  applicable by default.
- **The plan.** Section 8 of the plan gets a dated note with this rule.

## 4. Readers (D-A4)

### 4.1 On the host (no new dependency, no code from the file)

Two formats join `readers.py`:

- `lines:rows`: the number of non-empty lines (whitespace-separated text such as UCI
  `.data` files; a header, when there is one, is named by `lines:rows-1`);
- `arff:rows`: the number of non-empty, non-comment lines after the `@data` line (case
  insensitive); a file with no `@data` line gives no count.

Both also work inside a zip (`zip:<member>!lines:rows`).

### 4.2 In the paper's container (closed catalogue)

A split's `source` may be `reader:container:<reader>:<member>#<argument>`, with `<reader>`
one of the closed list below. The file read is always the dataset itself, where it is
mounted in the reader's folder (its data path); `<member>` names a member of that file
when it is an archive (exact name, empty for a bare file) and `<argument>` what the
reader needs (corrected on 2026-10-18 after the end-of-round review, to match the code):

| Reader | `<member>` | `<argument>` | Count |
|---|---|---|---|
| `cifar_python` | the member of the tar.gz (`cifar-10-batches-py/test_batch`, ...), or several joined by `+` | none | the length of the `labels` (CIFAR-10) or `fine_labels` (CIFAR-100) list of each pickled batch, summed |
| `excel` | a member of a zip, or empty for a bare Excel file | the sheet, by name or 0-based index | the data rows `pandas.read_excel` returns for that sheet (header row excluded) |
| `dgl` | empty (a bare file) | a canonical edge type `src,etype,dst` | the number of edges of that edge type in the first graph `dgl.load_graphs` returns |

- **Where it runs.** After the build, as one more container of the setup step
  (`setup/data/<dataset>`), in the image the ladder built, under the same sandbox as every
  run (no network, read-only root, the verified file mounted read only), with its CPU in
  the setup account and the build stage's time limits. The reader is a script of
  Refute's code (standard library, plus the library the format needs, imported from the
  paper's environment), written into the container's fresh folder; neither the claim nor
  the repository chooses or changes it.
- **What the repository can still influence, and what is blocked.** Blocked by
  construction: the working directory is the reader's own fresh folder (never the clone);
  the interpreter is called by its path in the image with `-I -S` and an argument list
  (no shell), so `PYTHONPATH`, the user site, the script's folder and the `site`
  processing (`.pth` files and `sitecustomize` installed by the build) are not used; the
  script adds to `sys.path` only the library folders of that interpreter
  (`sysconfig.get_paths()["purelib"]` and `["platlib"]`; for a venv, whose `sys.prefix`
  Python 3.12 and 3.13 leave at the base installation under `-S`, computed from the folder
  above the interpreter's own path when it holds `pyvenv.cfg`), without processing `.pth`
  files; the command starts with `/usr/bin/env -i` and the claim's thread variables, so no
  other variable of the image reaches the reader. The loader configuration of the image
  (for example a `/etc/ld.so.preload` written by the build) is not controlled: it is part
  of the residual trust below. A library
  that cannot be imported that way gives no count (`INCONCLUSIVE`), never a fallback to
  the normal start-up. Sources: https://docs.python.org/3.12/using/cmdline.html#cmdoption-I
  and https://docs.python.org/3.12/library/site.html, read 2026-10-18.
- **What it returns.** A file `counts.json`, created by this run in the reader's folder
  (absent before the run; a regular file, not a link; at most 64 KiB): one JSON object
  from split name to a non-negative integer, nothing else. The host parser refuses
  duplicate keys, booleans, floats, negative numbers, any content after the object, a
  missing or extra split, and a container that did not exit 0, ran out of time or of
  budget: each gives no count for that dataset, so `data_present` is `INCONCLUSIVE`
  (never an artifact cause). Selectors reach only the mounted artifact; a tar or zip
  member is named exactly, and an archive with two members of that name gives no count.
- **Residual trust, declared.** The reader imports the paper's interpreter and libraries,
  and `cifar_python` unpickles (unpickling can run code:
  https://docs.python.org/3.12/library/pickle.html, read 2026-10-18). A compromised
  environment can write a well-formed, false `counts.json`, so `data_present` could
  `PASS` wrongly on such a dataset. The checks above guarantee the structure of the
  answer, not its truth. `data_present` is a gate of presence and size; the evidence of
  the evaluation is `metric_extracted`, which keeps requiring its own observed count.
- **Proof on the real backend.** The subprocess tests show the logic only. Before a
  container reader is used on a paper, a run on the VM with the docker backend, on a
  synthetic file of that format, records the mounts, the working directory, the command
  line and the environment the reader saw, and its counts (a WP6-style record).
- **No container reader without a build.** With no image built, the reader does not run
  and the count is absent (`INCONCLUSIVE`); the build gate already decides the claim.

## 5. Out of this addendum

- **CMake builds (2502.16782).** Not supported in version 1 of the docker backend; a build
  that needs it ends without an image, `INCONCLUSIVE` by a limitation of Refute
  (`production.py:257`, `ladder.py:200-210`, `paper.py:226-262`). No code.
- **TensorBoard event files.** A metric written only to a TensorBoard event file
  (2407.11735, AUROC) is not extractable. A reader is added only if such a claim is drawn,
  before the lock, with its own acceptance text.
- **Per-unit value files** (one value per episode, 2407.20299): no new coverage route here.

## 6. Synthetic cases

**Must pass:**
- every existing claim resolves to the same full resolved hash (W3.5, `test_lock_compat`)
  and every existing test passes;
- a `repository_file` dataset whose file has the declared hash, size and split sizes:
  `data_present` `PASS`, coverage the count of the claim's split;
- a claim on a derived split: `data_present` `PASS` with the coverage of its
  `derived_from` splits; the coverage route compares its count with the derived split's
  `expected_examples`;
- a `generated` dataset: the resolution writes `not_applicable`; the claim's verdict comes
  from the other gates (a synthetic repository that prints its count reaches
  `REPRODUCED`), and the verdict records the gate as not applicable with its reason;
- the host readers: `lines:rows`, `lines:rows-1`, `arff:rows`, and each inside a zip;
- the container readers, run by the subprocess backend on synthetic files built by the
  test (a small CIFAR-like tar.gz, an `.xlsx` written with `openpyxl` when the test
  environment has it, a DGL file when `dgl` is installed; the cases needing a library the
  CI environment lacks are skipped and say so).

**Must fail** (rejected at validation, refused as input, or the check does not pass):
- `origin: generated` with a `url` or `sha256`; `repository_file` with an absolute path
  or `..`; a `generated` entry with no `generator`, or with an `inputs` name that is not a
  weights entry;
- `derived_splits` on a `generated` entry; an empty `derived_from`, or one naming no
  split; a derived split name equal to a split name;
- `metric.split` naming neither a split nor a derived split; `n_examples` different from
  the derived split's `expected_examples`;
- a claim that writes `not_applicable` by hand, or `not_applicable` on a dataset that is
  not `generated`;
- in the core: `not_applicable` naming a gate other than `data_present`, with an empty
  reason, together with a result, a failure cause or a minimum for that gate;
- a `generated` claim whose run prints no count: `metric_extracted` `INCONCLUSIVE`, the
  claim `INCONCLUSIVE` (zero coverage is never a pass);
- a `repository_file` with a different hash or size: `data_present` `FAIL`, the claim
  `INCONCLUSIVE`, never `NOT_REPRODUCIBLE`;
- `arff:rows` on a file with no `@data` line; a container reader whose `counts.json` has
  an extra key, a missing split, a float, a negative number, or that exits non-zero: no
  count, `data_present` `INCONCLUSIVE`;
- an unknown container reader name: refused at validation.

**Must fail, added after the design review (Codex, 2026-10-18):**
- the exemption: a claim file mixing origins where a `downloaded` claim carries the map;
  a minimum of `data_present` given by hand on a `generated` claim; a result given for
  the exempt gate while an earlier gate failed (still refused); a reason of spaces only;
  `run_completed` or `metric_extracted` absent or with zero coverage on a `generated`
  claim (`INCONCLUSIVE`); the map present in every verdict, `REPRODUCED` and
  `INCONCLUSIVE` alike; a run or a dossier whose map and origin disagree (error);
- derived splits: a repeated name in `derived_from`; one wrong file split while the sum
  of `derived_from` is right; a wrong file split outside `derived_from`; a sibling derived
  split missing from `other_splits`; two derived splits with the same labels hash;
- `repository_file`: a missing file; a symbolic link (as the file or as a folder on the
  path); a path that resolves outside the clone; the file changed by the build or a run
  after the check (the runs read the verified copy, so the change is not seen, and the
  test shows it); the count and the runs reading the same verified bytes;
- container readers: `counts.json` holding `true`, a duplicate key, truncated JSON,
  content after the object, more than 64 KiB, present before the run, or a symbolic link;
  a reader stopped by its time limit or by the budget; a planted `sitecustomize.py`, a
  `.pth` file, a `PYTHONPATH` and a file in the working directory named like a module the
  reader imports: none of them runs (the test proves it by a marker file that stays
  absent).

The cases that need a library the CI environment lacks are skipped and say so; a skipped
case never counts as the proof of its reader (the VM record of section 4.2 is).

## 7. Regression

`tests/test_lock_compat.py` (both requirements of W3.5), the WP2 core tests
(`tests/test_paper.py`), the schema tests and the integration tests run unchanged and
pass.
