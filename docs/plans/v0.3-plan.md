# v0.3 Replicate papers (ML pack): plan

## 0. Status

This is the official plan of phase v0.3. It was written on 2026-10-14, from a draft
of 2026-10-09 that was never published. [ROADMAP.md](../../ROADMAP.md) stays the
single source of truth for phases; where this plan and the ROADMAP differ, the
ROADMAP wins and this plan is corrected.

v0.3 was opened on 2026-10-14 by the maintainer's decision, as an explicit exception
to "How phases work": v0.2.1 did not pass a gate, none of its exit criteria is ticked
(all are deferred), and no gate review was run
([closure record](../validation/v0.2.1/population/closure-record.md), PR #36). The
exception covers only the transition from v0.2.1 to v0.3.

Every decision in this plan was taken by the maintainer on 2026-10-14 (section 13).
Several pre-decisions were adjusted after an external second opinion received on
2026-10-09 and accepted by the maintainer; its text is not published. Before its
merge, this plan was reviewed read-only by a second agent (Codex); the corrections
it raised were accepted by the maintainer on 2026-10-14 and are applied here.

This plan authorizes no paper selection, no execution of third-party code and no
lock. Each of those steps has its own commit, stop and approval (section 10).

**Not yet validated:** the isolation of third-party code (sections 6.1 and 7.1) is a
set of requirements. It is validated only by the acceptance tests of the VM work
package (WP6), before any third-party code runs.

## 1. Goal, scope and exit criteria

Re-derive published machine-learning results from their public code and data,
attack them, and give each claim a deterministic paper verdict.

**Scope (from the ROADMAP):** paper intake (arXiv ID or DOI plus public code and
data); claim extraction by an agent, approved by a human before the lock; sandboxed
reproduction from scratch in a container with resource limits; robustness attacks
(seeds, data splits, ablations, holdout); paper verdicts; right of reply (an email
draft and a waiting period before any negative result is published); consumer
hardware only.

**Not in v0.3:** discover mode, the swarm, other domain packs, GPU work (section 7.6),
additional papers beyond the main sample (section 10.4), automatic submission of
anything to anyone, and any judgment about authors.

**Exit criteria** (the same text is in the ROADMAP):

- 5 papers processed end to end (the main sample), with every verdict path,
  including `NOT_REPRODUCIBLE`, shown to be handled correctly by a controlled test
  (an artifact built to be non-reproducible), whether or not the real sample
  contains one.
- Right of reply: the notification was made and recorded; the reply period remains
  open.

**"Processed end to end".** A paper of the main sample counts as processed end to
end when all of the following hold:

1. its claims were approved and locked (section 5);
2. its run was made and its experimental core sealed (section 9.1);
3. the **dossier verification** (section 10.2) checks the execution states and the
   reasons of every interruption, and recomputes an identical claim profile from the
   recorded outputs;
4. its dossier has an independent reviewer report (section 10.3);
5. if any of its claims is negative, the notification was made and recorded
   (section 9).

The verdicts themselves do not matter for this criterion: a paper whose three
claims are `INCONCLUSIVE` is processed end to end if the five conditions hold.

**What the dossier verification shows.** Recomputing the verdicts from the recorded
outputs shows that the **classification is deterministic**. It does not show that
the **experiment is repeatable**: the main sample is not re-run (section 10.2).
Every public statement about a reproduction says so.

## 2. Principles applied to papers

| Principle | Consequence for the ML pack |
|---|---|
| Agents propose, deterministic tests decide | The agent proposes claims and run commands; a human approves; only versioned code computes verdicts. No agent debugs or patches a repository during a locked run. |
| Pre-registration lock before hidden data | Papers, claims, tolerances, attacks, seeds, build ladder and budget are locked before any paper code of the main sample is executed. The hidden data is the reproduction output itself. |
| Public randomness after the choices it governs | The randomness of each drand round is revealed only after what it selects from is frozen and published; the round itself may be identified in advance, in the protocol (sections 4.3, 5.2). |
| Never invent facts | Paper metadata from arXiv; repository facts from GitHub; reported numbers quoted from the paper with their location (table, row, column, page). Every source with its retrieval date. |
| Never submit automatically | Email drafts are generated; the maintainer sends them from their own account. Nothing is posted to arXiv, OpenReview, MLRC or any venue. |
| Verdicts about claims, never authors | Verdicts attach to a claim at a pinned paper version and repository commit. No claim alone defines a paper (section 8.3). Templates avoid words about people. |
| Negative results only after right of reply | Negative claim verdicts stay private until the gate is passed and the reply period has ended (section 9). |
| Out of scope: medical, dual-use biology or chemistry | Mechanical keyword filter plus human check at triage (section 4.2). |
| No network in unit tests and CI | Synthetic toy papers (small local repositories with injected effects) test every verdict path offline (section 11). |
| No PASS without examined data (issue #15) | Coverage units and minimum coverage for every check; zero or insufficient coverage never yields `REPRODUCED` (section 8.4). |
| CPU-heavy work spread over cores, within limits | Refute's own processes run with CPU affinity on threads 8 to 31; third-party code runs in a VM with 24 virtual processors (section 7). |

## 3. Prior art

- **CORE-Bench** (arXiv 2409.11363, 2024): agents install and run a paper's
  repository and answer questions about its outputs; running someone else's
  repository is the hard part, so `NOT_REPRODUCIBLE` is expected to be common.
- **PaperBench** (arXiv 2504.01848, 2025): agents replicate papers from scratch,
  graded by an LLM judge. Refute must not use an LLM judge as the final verdict.
- **ARA, Agentic Reproducibility Assessment** (arXiv 2605.02651, 2026): workflow
  graphs extracted from papers, evaluated on ReScience C articles.
- **MLRC 2026** was an official NeurIPS 2026 track for reproducibility studies
  accepted in TMLR; its window closed on 2026-09-30 (checked 2026-10-14). A possible
  later publication path for Refute results, always human-driven; v0.3 plans no
  submission.
- **ReScience C**: peer-reviewed journal of replications.
- "Position: Machine Learning Conferences Should Establish a 'Refutations and
  Critiques' Track" (arXiv 2506.19882): context for how negative results are
  received.

What Refute adds: pre-registration with a hash lock and a public random draw,
deterministic verdicts with coverage, robustness attacks and a right-of-reply
period. None of the works above combines these (not verified exhaustively).

## 4. Choosing papers

Papers are drawn, never hand-picked.

### 4.1 Sampling frame (D-1)

The frame is the Papers with Code archive on Hugging Face,
`pwc-archive/links-between-paper-and-code`: about 300.2 thousand paper-to-repository
links in one Parquet file of 41.4 MB, CC BY-SA 4.0, snapshot of 2025-07-28, marked
"will not be updated" (checked 2026-10-14). Columns used: `paper_arxiv_id`,
`repo_url`, `is_official`, `mentioned_in_paper`, `framework`.

The file is snapshotted before any draw; its URL, revision and SHA-256 go into the
protocol. arXiv is the authoritative source for each walked paper's metadata, GitHub
for the repository state.

**Declared bias:** the archive stops in July 2025, so every drawn paper is more than
15 months old at selection. Older repositories break more often (unpinned
dependencies, moved data, deleted weights), which raises the chance of
`NOT_REPRODUCIBLE`. This bias is stated in the protocol and in every report that
gives a rate.

**License of derived lists:** any list derived from the archive that Refute
publishes (frame snapshot, filtered frame, shuffled walk, selection log) is released
under CC BY-SA 4.0 with attribution.

### 4.2 Mechanical filters

Applied to the frame before the draw by a script; the count after each filter goes
into the selection log.

1. Rows with the same `paper_arxiv_id` and `repo_url` are deduplicated.
2. `is_official = true` and `mentioned_in_paper = true`.
3. A valid new-style arXiv ID (`YYMM.NNNNN`) whose year-month is in the window
   **2023-01 to 2025-06** (D-2).
4. arXiv primary category in **`cs.LG` or `stat.ML`** (D-2), checked only for walked
   papers; a walked paper outside the list is rejected with that reason.
5. One paper, one repository: a paper with more than one official repository is
   rejected (`ambiguous_repository`), not resolved by choice.
6. Out-of-scope keywords in title or abstract (list fixed in the protocol) lead to
   rejection. A human may add rejections only for the CLAUDE.md out-of-scope
   reasons, never remove one.
7. Every paper of the pilot rounds (section 4.5) is removed from the main walk.

**Adjustment by the pilot (D-2).** The window and the category list may be adjusted
at most **once**, before the protocol commit, and only by an **ordered list of
alternatives with a trigger**, both fixed in the pilot protocol before the pilot
round (for example: "if fewer than k of the 20 are accepted, apply the first
alternative of the list"). The first alternative whose trigger fires is applied;
there is no choice among alternatives. The reason is recorded.

### 4.3 Draw of the papers

1. The protocol fixes a future drand mainnet round (default chain, as in v0.2). The
   protocol, the selection script and the frame snapshot hash are committed and
   pushed before that round is published.
2. After the round: verify the BLS signature and derive `seed = int(randomness, 16)`.
   The code comes from `calibration/v0.2/select_targets.py` (`round_time`,
   `verify_beacon`, `drand_seed`), tested by `tests/test_drand.py`; moving it into a
   shared module is part of the selection work package, with its acceptance
   document.
3. Sort the filtered frame by arXiv ID and shuffle it with `random.Random(seed)`.
4. Walk the shuffled list in order. Each candidate goes through triage (section 4.4)
   and is logged `accepted` or `rejected`, with one reason from a closed list and
   its evidence.
5. The **main sample** is the first 5 eligible papers in walk order (D-19).
6. If drand is unavailable or the signature fails: stop; the maintainer decides. An
   agent never switches the source of randomness.

### 4.4 Triage

Triage reads metadata, the paper and the repository files. It never executes
repository code.

**Closed list of rejection reasons** (fixed in the protocol): `out_of_scope`;
`no_license` (no license **or explicit compatible authorization** in LICENSE,
README or other relevant files; a public repository is not an unrestricted
permission; D-5); `data_requires_registration_or_terms` (an operational choice,
declared in every report, never presented as a scientific failure of the paper);
`data_license_incompatible`; `weights_license_incompatible` (licenses are checked
even when the download is open); `outside_v03_experimental_scope` (no measurable
number; D-7); `data_not_public`;
`needs_paid_api_or_credentials`; `stated_compute_over_budget`; `requires_gpu`
(stated or hard-coded CUDA with no CPU path); `dataset_over_budget`;
`pretrained_download_over_budget`; `ambiguous_repository`;
`repository_unavailable`; `no_reproduction_instructions`; `category_outside_list`.

**Thresholds** (fixed now):

| Reason | Threshold |
|---|---|
| `dataset_over_budget` | declared datasets above **5 GB** in total |
| `pretrained_download_over_budget` | declared model weights above **2 GB** in total |
| `stated_compute_over_budget` | compute stated by the paper or README for producing the claims above the **192 CPU-hours of the base reproduction** (section 7.3), not the 384 of the whole paper; compute stated only in GPU time leads to `requires_gpu` |

- "Looks hard", "looks broken" or "probably won't reproduce" are **not** reasons. An
  install that might fail is what the run measures.
- Exclusions are counted and reported; they are never a judgment on the paper's
  scientific quality.
- The agent proposes each decision with evidence (file and line, paper page); the
  maintainer approves every acceptance and every rejection, in the selection log.
- The rejection profile is itself a result and is reported.
- The independent reviewer receives the selection log and checks the rejections.

**Named denominators.** Every report gives them separately: papers walked; papers
excluded, by reason; papers admitted to the main sample; claims selected; claims by
verdict. A "rate" always names its numerator and denominator; the result of a paper
is a claim profile, not a single verdict (section 8.3), so there is no "rate of
reproduced papers".

### 4.5 Pilot and development papers (D-3, D-4)

Before the protocol commit, a **pilot** triages 20 papers drawn from a **separate**
drand round, reading only metadata and README, never running code. It estimates the
rejection rate and may trigger the one frame adjustment of section 4.2.

A pilot acceptance is **provisional**. The **2 development papers** are the first 2
papers accepted by the pilot that then pass the **full triage** (section 4.4); if one
fails it, the next provisional acceptance is tried, in pilot order. If the 20 pilot
papers do not yield 2 development papers, **at most one additional pilot round** is
drawn under the same rules; if that is still not enough, the phase stops for the
maintainer's decision.

The development papers stay outside the main sample. They are used before the lock
only to find engine crashes, I/O errors and accounting errors, and to exercise the
experimental reproduction (section 10.2); never to set or tune a threshold, a
tolerance or a budget (as in v0.2).

## 5. Claims

### 5.1 What a claim is

One claim is one quantitative statement that the repository documents how to
produce:

```yaml
- key: arXiv-2401.01234v2-C1
  type: value            # value | comparison
  statement: "Method X reaches 91.2% test accuracy on Dataset Y."
  source: {arxiv_id: 2401.01234, version: 2, location: "Table 2, row 'X', column 'Acc'",
           quote: "91.2 ± 0.3", retrieved_utc: ...}
  metric: {name: accuracy, split: test, higher_is_better: true,
           reported: 91.2, reported_sd: 0.3, reported_n_seeds: 5, unit: percent}
  comparison_mode: two_sided   # value claims: two_sided | one_sided_at_least | one_sided_at_most
                               # comparison claims: direction | margin | magnitude (section 6.2)
  scope: full_training         # full_training | checkpoint_evaluation
  run: {command: "python train.py --config configs/y.yaml", workdir: ".",
        metric_extraction: {file: "results/metrics.json", json_path: "$.test.acc"}}
  tolerance: {...}       # section 6.2
  coverage_minimum: {...}  # section 8.4
  attacks: [...]         # section 6.3, applicability and order decided before the lock
```

Metric extraction is deterministic (a JSON path, a CSV column or a regular
expression on the log, fixed before the lock). No LLM reads outputs to decide a
value. The exact schema is fixed in the claim-spec work package.

### 5.2 Which claims (D-6)

The claims of each paper are drawn from a **frozen and published inventory**, with a
drand round of their own. The paper draw's seed is known when claims are listed, so
it is never used to draw claims.

1. **Inventory.** For each of the 5 papers, the agent lists every numeric result in
   the paper's main-results tables (those referenced in the abstract or
   introduction as the main result) that the repository's instructions can produce
   within the budget. Rules fixed in the protocol:
   - **granularity:** one numeric cell is one candidate;
   - **canonical ID:** table, row and column as printed in the paper;
   - **order:** reading order of the paper;
   - **eligibility** rules and the closed list of exclusion reasons.
2. **Approved before the draw.** For every candidate, the maintainer approves its
   transcription (value, location, metric, split, command), its type (`value` or
   `comparison`) and, for a comparison, its reference method. Each candidate names
   the method and its comparison reference, the dataset and split, the metric and
   the published number, and the execution conditions; a comparison claim
   evaluates the difference between methods under equivalent conditions.
   Whether a paper has an **eligible comparison** is determined by the rules of the
   protocol and approved with the inventory, before it is frozen; never from the
   draw or from any run.
3. **Frozen and published.** The 5 inventories, their SHA-256 hashes and the
   implementation of the claim draw are committed **and pushed** before a **future
   drand round reserved for the claims**, fixed in the protocol. If they are not
   published before that round, the round cannot be used for them.
4. **Draw.** For each paper:
   `random.Random(int.from_bytes(sha256(claim_seed_bytes || arxiv_id_utf8), "big"))`
   shuffles the inventory, and the first **K = 3** candidates are drawn (D-6):
   - **if the frozen inventory has at least one eligible comparison**, a comparison
     is required: if none of the 3 drawn is a comparison, the 3rd is replaced by the
     first comparison in the shuffled order;
   - **if it has none**, the paper stays in the sample and up to 3 value claims are
     drawn; its dossier states explicitly that no comparison was evaluated.

   The absence of a comparison is never a reason to exclude a paper. If the
   inventory has 3 candidates or fewer, all are taken. The drawn order is the claim order used by the budget
   (section 7.3) and by the report (section 8.3).
5. **After the draw.** Only corrections of transcription that keep the scientific
   identity of the candidate are allowed, each recorded. A drawn candidate may be
   invalidated only for a reason of a closed list fixed in the protocol; the
   original record is kept, and the next candidate in the shuffled order replaces
   it, of the same type when the comparison requirement must be kept. A candidate
   is **never** replaced because of an unfavorable result, an observed cost or an
   `INCONCLUSIVE` verdict.

### 5.3 Paper with no measurable number (D-7)

Excluded at triage and counted as `outside_v03_experimental_scope`. It is never
`NOT_REPRODUCIBLE` and never a judgment on the paper's quality.

### 5.4 Definitions required before the lock

Each claim specifies, before the lock:

| Definition | Where |
|---|---|
| The tolerance for counting the result as reproduced, and the comparison mode | `tolerance`, `comparison_mode` (section 6.2) |
| Seeds, repetitions and how variability is treated | base run seeds (6.2) and the `seeds` attack (6.3) |
| The robustness changes that can produce `FRAGILE`, and their order | `attacks`, with applicability and order decided before the lock (6.3, 7.4) |
| The minimum coverage of each check, for a positive and for a negative conclusion | `coverage_minimum` (section 8.4) |
| The scope: full training, or evaluation of a released checkpoint | `scope`; a checkpoint evaluation also follows the checks on model weights (6.1) |
| What separates a limitation of Refute from an impossibility to reproduce | engine-side versus artifact-side reasons (section 8.2) |

A claim that does not specify all of these is not ready to lock.

### 5.5 Recording approvals

Approvals are part of the locked claim: `approved_by`, `approved_utc` and the commit
in which the maintainer approved. The published inventory, including candidates not
drawn, is an attachment covered by the lock, so the choice inside a paper is
auditable.

## 6. Reproduction, tolerance and attacks

### 6.1 Isolated environment and pinned inputs

These are requirements. Each one is tested in the acceptance document of the VM work
package (WP6) before any third-party code runs; until then the isolation is **not
validated**.

- **Where:** third-party code runs only inside a dedicated Hyper-V VM on the
  maintainer's PC, with Docker inside (D-9; section 7.1). Docker Desktop on Windows is
  used only for Refute's own tests. Never the maintainer's existing VPS.
- **Network blocks enforced outside the guest.** Access from the VM to the Windows
  host, the local network and private or special address ranges (IPv4 RFC 1918 and
  link-local; IPv6 unique-local, link-local and the other special-purpose ranges of
  the IANA registry) is blocked by **access control lists on the VM's network
  adapter port in Hyper-V**, set by the maintainer on Windows. A firewall inside the
  guest is only a second layer, since a compromised guest could change it.
- **Build egress only through an allowlist.** During the build, the VM reaches the
  internet only through a controlled intermediary (a forwarding proxy) with an
  allowlist of declared destinations: package registries and the declared data
  hosts. There is no direct connection to the internet.
- **Declared inputs fetched by Refute.** Declared datasets and model weights are
  downloaded by Refute's own fetcher, not by repository code, and hashed before any
  repository code runs. Downloads made by the repository's own build happen only in
  the build phase and are logged.
- **Run phase without network:** `--network none`, and the VM's network adapter
  disconnected.
- **Container per run**, base image pinned by digest; Python version from the
  repository or from a fixed ladder.
- **Limits per container:** CPU, memory, process count, active-time limit, disk
  quota; `--cap-drop ALL`, `--security-opt no-new-privileges`, non-root user,
  read-only root filesystem with a writable work volume.
- **No mounts and no credentials.** No folder of the Windows host and no folder of
  the guest is mounted into a container, except one output directory of that
  container. Never mounted or passed: the Docker socket, devices (`--device`),
  `--privileged`, an SSH agent, credentials, git configuration or host environment
  variables.
- **Builder configuration, verifiable.** The BuildKit entitlements
  `network.host`, `security.insecure` and `device` are forbidden; the builder
  configuration file is recorded in every dossier.
- **Repository version (D-8):** frozen by commit. Use the version explicitly
  associated with the result (a tag or commit named in the paper or README); without
  one, the latest commit on the draw date. Record the paper version, the chosen
  commit and the latest commit; tags are resolved to commits. An alternative version
  may be evaluated only as a separate experiment defined beforehand; the main
  version is never replaced after a result is seen.
- **Datasets and model weights:** publish the reference, version, license, retrieval
  date and hashes; keep a local copy for execution and reproduction only when the
  license allows; check the license even when the download is open.
- **Deterministic build ladder** (fixed before the lock, no free-form agent fixes):
  1. the repository's own Dockerfile or `environment.yml` / lock file, as is;
  2. its `requirements.txt` resolved with `uv pip compile --exclude-newer <date of
     the pinned commit>`;
  3. step 2 with the next Python version of the ladder.

  The first rung that builds is used; all attempts are logged. The attribution of a
  failure follows section 8.2.
- **Allowed patches:** only a list fixed and hashed before the lock (for example
  forcing CPU through an environment variable). Every patch is a diff in the
  dossier. Source edits after the lock are forbidden.
- **Who executes:** every sandboxed run is started by the maintainer or with the
  maintainer's explicit approval for that paper. An agent never executes repository
  code on the host.
- **CI:** cannot pull images (no network), so the container backend is tested
  locally; CI tests a `subprocess` backend with the same interface on synthetic
  repositories.

### 6.2 Base reproduction and tolerance (D-10)

For one number:

```
tolerance = max(abs_floor, rel_tol * |reported|, k_sd * reported_sd)
```

Defaults: `rel_tol = 0.02`, `k_sd = 2`, and `abs_floor` per metric scale (for
example 0.5 percentage points for an accuracy in percent). Without a published SD the
`k_sd` term is absent. Per-claim overrides only before the lock, with a written
reason. A non-finite value does not pass the gate `metric_extracted`.

**The mode comes from what the claim states**, written in the claim
(`comparison_mode`) before the lock. The field `higher_is_better` alone never decides
it.

**Value claims:**

| What the paper states | `comparison_mode` | Reproduced when |
|---|---|---|
| A published value "X" | `two_sided` | \|x_rep − X\| ≤ tolerance |
| A bound, "at least X" | `one_sided_at_least` | x_rep ≥ X − tolerance |
| A bound, "at most X" | `one_sided_at_most` | x_rep ≤ X + tolerance |

**Comparison claims.** `d` is the difference between the method and its reference,
**oriented so that a positive `d` is an advantage in the claimed sense**; the
orientation is written in the claim before the lock.

| What the paper states | `comparison_mode` | Reproduced when |
|---|---|---|
| A direction only | `direction` | d_rep > 0 (a tie does not keep the direction) |
| A minimum published margin g_pub | `margin` | d_rep ≥ g_pub − tol_d **and** d_rep > 0 (the tolerance never admits a tie or an inversion) |
| A published difference d_pub | `magnitude` | \|d_rep − d_pub\| ≤ tol_d |

A claim that states a direction and a margin uses `margin`, which requires both.
Each mode keeps the meaning of the original statement; it is chosen before the
lock.

`tol_d = sqrt(tol_m² + tol_b²)`, where `tol_m` and `tol_b` are the tolerances of the
two numbers. This is an **operational acceptance convention**. It is not a
confidence interval and does not claim a demonstrated statistical uncertainty: the
individual tolerances are not necessarily standard deviations, and the compared
results may be correlated. When the paper publishes an uncertainty of the paired
difference, that value is used instead; the treatment of its absence is fixed before
the lock.

Equality at the limit counts as reproduced for the value modes and for `magnitude`;
it never does for `direction` or for the `d_rep > 0` part of `margin`.

Outside tolerance, the dossier records the value obtained, the difference and the
quantitative reason. It infers neither an error in the paper nor a change of
configuration.

If the paper reports a mean over n seeds, the base run uses n seeds, capped by the
budget; the cap is fixed before the lock.

### 6.3 Robustness attacks

Applicability of each attack to each claim, and the effective order of the attacks
(section 7.4), are decided before the lock and approved by the maintainer, never
after results.

General rules for every attack:

- a missing, interrupted or invalid run never counts as a scientific failure;
- a **valid failure** (a run that completed with its prerequisites met and fails
  the attack's predicate) can establish `FRAGILE`;
- with no valid failure and incomplete coverage, the attack is `INCONCLUSIVE`;
- `seeds` and `data_split` use the same predicate as the claim (section 6.2): a
  `magnitude` claim is attacked on magnitude, not only on direction, and the
  one-sided modes stay one-sided. `holdout`, `leakage`, `trivial_baseline` and
  `ablation` keep their own predicates, given in the table.

| Attack | Rule | Failure means |
|---|---|---|
| `metric_recompute` | Where the run saves predictions: recompute the metric with an independent implementation and compare it with the printed value. Part of the base reproduction check (section 7.3). | `NOT_REPRODUCED` if they disagree beyond rounding (fatal) |
| `seeds` | 5 extra seeds drawn from the per-paper seed. The claim's predicate must hold in at least 4 of the 5 runs, and the claim's predicate applied to the mean of the 5 runs must hold too (one-sided modes stay one-sided). Two valid failures establish `FRAGILE`. | `FRAGILE` |
| `data_split` | Only if the paper uses a random train/validation split: 3 re-splits with the same proportions. The claim's predicate must hold in **3 of 3** splits, a conservative choice of this protocol; it is not claimed that the tolerance absorbs all variation between splits. One valid failure establishes `FRAGILE`. Fixed benchmark test sets are never re-split. | `FRAGILE` |
| `ablation` | Only if the paper claims a component matters and the repository exposes a flag or config to disable it: the claimed gap holds in the claimed sense. No source edits. | `FRAGILE` |
| `holdout` | A split carved from the training data with the per-paper seed before training, unseen until evaluation; the claim must hold within a wider, pre-registered tolerance. | `FRAGILE` |
| `leakage` | Exact-duplicate check between train and test examples (hash of each example). | `FRAGILE` above a fixed overlap fraction |
| `trivial_baseline` | Majority-class or random baseline on the same split; the claim must beat it by more than tolerance. | `FRAGILE` |

## 7. Machine, affinity and budget

### 7.1 Where code runs (D-9) and hardware (D-11)

- **Machine:** the maintainer's PC. Checked on 2026-10-14 (read only):
  AMD Ryzen 9 5900XT, 16 cores and 32 threads; 63.9 GB of RAM; Docker 29.8.2; free
  disk 344.0 GB on C: and 326.8 GB on K: (`Win32_Processor`,

  (SHA-256 checked); 24 virtual processors; 48 GB of static memory; one VHDX for
  system, images and cache, with a differencing disk per paper so every paper starts
  from the same clean state; no shared folders, Enhanced Session off, Guest Service
  Interface off; network blocks and egress allowlist as in section 6.1; results
  pulled by the host over SSH with a key used only for this VM. Built by the
  maintainer (it needs administrator rights). Its isolation is validated only by the
  acceptance tests of WP6.
- **CPU only.** At most 24 of the 32 threads are used. Hyper-V limits the number of
  virtual processors; it does not pin specific cores. Thread counts inside the
  containers (`OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS` and
  similar) are fixed by the claim, so changing the CPU limit never changes how a
  computation is split.
- **No paid fallback.** The financial budget of v0.3 is zero. If the VM cannot be
  built or hardened, the phase pauses for a decision of the maintainer; nothing is
  contracted. (For reference only: on 2026-10-14 every Hetzner CCX plan showed
  "currently unavailable" and the CCX53 was listed at EUR 0.8558 per hour,
  hetzner.com/cloud/general-purpose; DigitalOcean CPU-Optimized 32 vCPU was USD 1.00
  per hour, digitalocean.com/pricing/droplets. Akamai São Paulo prices were not
  re-verified.)

### 7.2 Refute's own processes on the host

- Refute's own processes (tests, orchestration, selection) run with CPU affinity on
  threads 8 to 31 (mask `FFFFFF00`).
- The default number of workers is the **number of CPUs the process is allowed to
  use by its affinity mask, minus 2**. `os.cpu_count()` is not assumed to reflect the
  affinity. With the mask `FFFFFF00` (24 CPUs) the default is 22 workers. The
  setting stays configurable.
- The acceptance document of the work package that implements this includes a test
  of it on Windows.

### 7.3 Budget per paper

The unit is **CPU-hours**: CPU time summed over the processes of the experiment, read
from the cgroup of each container (`cpu.stat`, `usage_usec`). Logical CPUs are
neither physical cores nor equivalent between machines, so the CPU model is
recorded with every run.

| Rule | Value |
|---|---|
| Limit per paper | **384 CPU-hours, fixed.** The development papers check the accounting and the execution paths; they do not change the number. |
| What counts | The consumption of the processes of **all containers of the paper**, including builds (every rung of the ladder), downloads inside containers, base runs, `metric_recompute`, attacks, attempts, retries and repetitions. Refute's orchestration on the host is recorded separately. **Experimental work is never moved to the host** to escape the accounting. The meter of the builder and the single attribution of shared costs are specified in the acceptance document of the accounting work package. |
| Base reproduction | At most **192 CPU-hours**: the common setup, the base runs of all claims, and the applicable `metric_recompute`. |
| Attacks | **192 CPU-hours plus whatever the base reproduction did not use.** No transfer from the attacks to the base reproduction after the lock. |
| Status of the split | A choice of priority, not a split shown to be optimal. |
| Common setup | The environment build and the shared downloads are charged first to the base reproduction, in a separate "setup" account (S CPU-hours). If the setup exhausts the base budget, every claim is `INCONCLUSIVE` (`budget_exhausted`, `setup`). |
| Base reserve per claim | (192 − S) / n_base, where n_base is the total number of selected claims. Example: 3 claims and S = 30 give 54 CPU-hours per claim. |
| Sharing rule (reserve) | Each claim may use the remaining balance of the pool minus the reserves of the claims that have not run yet. Leftovers stay available to the following claims. |
| Attack pool and its claims | After **all** base runs: record and freeze the list of claims eligible for attacks, the balance and the reserves. n_attack = the number of claims whose base reproduction was obtained and that have at least one applicable attack (applicability fixed before the lock). The initial attack pool is 192 + the base balance; the reserve per claim is pool / n_attack, with the same sharing rule. Eligibility is never recomputed from the results of attacks. **This changes the earlier definition** (pool / total number of claims): attacks are not run on a claim whose base ended `NOT_REPRODUCED`, `NOT_REPRODUCIBLE` or `INCONCLUSIVE`, so reserving budget for it would waste it. |
| n_attack = 0 | No attack runs and the pool is not distributed; this is recorded. The balance stays unused, and the verdicts come from the evidence already obtained. |
| Claim order | The drawn order (section 5.2), never reordered after results are seen. The accounting is sequential by claim; parallelism exists only inside a claim (for example seeds), so a claim's limit never depends on which run finished first. Filtering the claims eligible for attacks keeps the drawn order. |
| Attempts and retries | The maximum number of attempts and retries of each stage is fixed before the lock. |
| Development papers | **96 CPU-hours each**, same accounting, including their experimental reproduction (section 10.2). No verdict is counted. |
| Estimate | 5 × 384 = 1920 CPU-hours, about 80 hours in an ideal estimate with 24 CPUs in continuous use. Not a maximum duration: preparation, downloads, pauses and reviews add time. |

**Operational guards, separate from the budget.** Active time and wall-clock time are
recorded and are never the budget limit. The guards are separate from the CPU-hour
budget: a run stops after **2 hours of active time without verifiable progress**,
and after a separate limit on active time. The values and the progress signals of
each stage are fixed before the lock. User-requested pauses are excluded from the
guard clock. An interruption by a guard is `INCONCLUSIVE` with an operational reason;
it does not, by itself, show a defect in the authors' code.

### 7.4 Order of the attacks

The order applies **inside each claim**; claims run in the drawn order. A default
priority, fixed before the lock, without claiming universal costs:

1. checks needed to trust the base reproduction (`metric_recompute`, part of the
   base budget);
2. applicable attacks with the lowest estimated cost;
3. attacks that need new complete runs.

The effective order and the applicability are recorded for each claim before the
runs. Nothing is reordered after results are known.

### 7.5 Capacity control while runs are in progress

Requirements: leave at least 8 threads to Windows; change the CPU limit and restore
it while runs continue; pause and resume a run without losing its state.

- **Containers (inside the VM):** `docker update --cpus N` changes only the CPU
  quota, never `--cpuset-cpus`; `docker pause` / `docker unpause` freeze and resume
  the processes.
- **Whole VM (Windows, administrator):** `Set-VMProcessor -Maximum`, `Suspend-VM` /
  `Resume-VM`, `Save-VM` / `Start-VM`, in a small documented PowerShell script run by
  the maintainer. Whether `-Maximum` can change while the VM runs is verified on the
  VM before the protocol.
- **Proposed commands:** `refute throttle --cpus N`, `refute throttle --reset`,
  `refute pause`, `refute resume`, `refute status`. Every throttle, pause and resume
  is recorded as an event with a UTC timestamp in `run/events.jsonl`. A heartbeat
  every 10 s inside the VM records gaps longer than 30 s as pauses.
- CPU-hours do not grow during a pause. Throttling keeps the budget from being
  consumed only because more wall-clock time passed; it does not guarantee
  identical consumption, since efficiency can change. A claim whose code depends on
  wall-clock time is flagged at triage.
- **Pre-run memory check:** before each run and each container, Refute checks that
  enough memory is free for the containers' limits plus a margin, and refuses to
  start otherwise, with a clear message. A refusal is logged and never counts
  against the budget.

### 7.6 Not in v0.3: the GPU

The maintainer's AMD Radeon RX 7800 XT is supported by ROCm on native Linux and on
WSL2 (AMD ROCm documentation, read on 2026-10-09), but most paper code targets CUDA,
and using the GPU inside Docker Desktop or a Hyper-V VM was not researched. Using it
is recorded as an item for a later phase, outside v0.3.

## 8. Verdicts and coverage

### 8.1 Gates, prerequisites and the order of verdicts

**Gates of the base reproduction:** `environment_build`, `data_present`, and
`run_completed` and `metric_extracted` of the **base** runs.

**Prerequisites of an attack:** the run and the metric of **that** attack. An
interruption or a failed prerequisite of an attack makes only that attack
`INCONCLUSIVE`; it never reopens the base reproduction.

Deterministic order for each claim. It deliberately differs from the order used for
discovery verdicts in `docs/verdicts.md`, so that a valid robustness failure is not
erased by an attack that did not run:

0. coverage enforcement (section 8.4);
1. a gate of the base reproduction that did not pass: `NOT_REPRODUCIBLE` or
   `INCONCLUSIVE`, by the attribution rule of section 8.2;
2. a valid fatal failure (`base_reproduction`, `metric_recompute`):
   `NOT_REPRODUCED`;
3. a base reproduction that is incomplete, with no valid negative conclusion:
   `INCONCLUSIVE`;
4. any attack with a valid failure and its prerequisites met: `FRAGILE`; the attacks
   not executed are recorded and the incomplete coverage is flagged;
5. any expected attack missing or `INCONCLUSIVE`: `INCONCLUSIVE`, with the status
   "Basic reproduction obtained; robustness inconclusive";
6. otherwise: `REPRODUCED`.

"Basic reproduction obtained" is declared only after `metric_recompute`, where it
applies.

### 8.2 `INCONCLUSIVE` and the attribution of failures (D-12)

`INCONCLUSIVE` is added to the paper verdicts: Refute could not decide, for reasons
on its side. It is treated as a possibly correct answer that is less informative,
with no value judgment.

This changes `CLAUDE.md` and `docs/verdicts.md` in a separate pull request right
after this plan, before any code; the `PaperVerdict` enum changes in the core work
package, with its tests.

**Attribution, at every stage** (build, data, run, metric, attacks):

- **`NOT_REPRODUCIBLE`** only for a failure of the artifact's own documented
  procedure, shown by complete attempts:
  - every rung of the build ladder ran to its end and failed with an error of the
    procedure itself; or
  - the documented command fails in the built environment; or
  - a declared artifact answers as absent (for example HTTP 404 or 410) in all of the
    N attempts fixed before the lock, spaced by an interval fixed before the lock.
- **`INCONCLUSIVE`** for everything else: an exhausted budget, an operational guard,
  an error of Refute, a transient network failure, a stage interrupted before its
  end, or an undetermined cause.

### 8.3 Partial results and the paper result

**Verdicts are per claim.** An exhausted budget does not erase a conclusion already
shown with its prerequisites met:

- budget exhausted during the base reproduction, with no conclusion: `INCONCLUSIVE`
  (`budget_exhausted`), never `NOT_REPRODUCIBLE`;
- base reproduction obtained, robustness incomplete, and no valid negative
  conclusion: `INCONCLUSIVE`, with the status **"Basic reproduction obtained;
  robustness inconclusive"**;
- a claim already shown to be `NOT_REPRODUCED`, or `FRAGILE` by a valid failure:
  the conclusion is kept, and the remaining checks are recorded as not executed.

Partial values go into the dossier as information only.

**The paper result is the claim profile, never a single verdict.**

- The report always shows the full profile of the claims, in the drawn order, with
  `INCONCLUSIVE` in the denominators.
- A headline appears only when every claim has the same verdict, with count and
  scope, for example "3 of 3 drawn claims: REPRODUCED". Otherwise the headline is
  "Mixed results: see the claims".
- No single claim defines the paper.
- A paper whose claims are all `INCONCLUSIVE`, or `INCONCLUSIVE` and `REPRODUCED`, is
  described as inconclusive for those claims, **never as positive or reproduced**,
  and stays in the denominators.
- Any negative claim verdict starts the right of reply for that paper.

### 8.4 Coverage units and minimum coverage (issue #15)

Each check has a coverage unit and a **minimum coverage**, fixed per claim before the
lock, separately for a positive and for a negative conclusion (for example, the base
reproduction must complete the number of seeds declared in the claim). Coverage below
the minimum gives no conclusion; it never yields a pass, and it yields a negative
conclusion only where the valid evidence already obtained establishes it
(section 8.1).

| Check | Coverage unit | Zero coverage means |
|---|---|---|
| claim extraction | approved claims | the paper cannot be `REPRODUCED` |
| `data_present` | examples per split (train, validation, test, holdout) | an empty split, or one smaller than the paper states (tolerance fixed), does not pass the gate |
| `metric_extracted` | examples the metric was computed on | a metric on zero examples does not pass the gate |
| `base_reproduction` | runs completed | no run: not decided |
| `seeds`, `data_split` | valid runs completed | `INCONCLUSIVE`, never PASS |
| comparison | paired comparisons made | nothing compared: `INCONCLUSIVE` |
| the repository's own test suite (D-13) | tests collected and not skipped | zero collected or all skipped: `INCONCLUSIVE` for that check, never PASS |
| `leakage` | example pairs hashed | `INCONCLUSIVE` |

The repository's own test suite is information only: its result is reported with its
coverage and never decides a verdict (D-13). Every row gets a synthetic case that
must not pass and one that must.

## 9. Right of reply

### 9.1 Seal, embargo and flow

1. **Seal.** When a locked run finishes, the **experimental core** of each dossier is
   sealed: the locked claims, the outputs, the logs, `verdict.json` and its
   manifest. The SHA-256 of a deterministic archive of all cores (and one per paper)
   is committed and pushed at once, with no content. The core never changes after
   the seal.
2. **Annexes.** Reviewer reports, the `reply/` records and the authors' reply are
   **annexes**, each with its own manifest that cites the hash of the sealed core.
   When an annex is added, the SHA-256 of its manifest (`ANNEX.json`) is committed and
   pushed at once, with no content, like the seal hash (decided by the maintainer on
   2026-10-15). The published dossier lets anyone verify the original core and each
   annex. Manual comparison of a dossier against the complete published list of annex
   manifest hashes can reveal a replaced or wholly removed annex; `refute
   check-dossier` does not perform this comparison.
3. **Embargo.** Until a paper's results may be published, every public commit or
   issue about it contains only hashes or neutral metadata.
4. **Draft.** `refute reply-draft <dossier>` writes an email draft in English to the
   corresponding author address printed in the paper (no other source of personal
   data is searched): the claim and its location, the paper version and commit
   tested, the verdict and its meaning, exact reproduction commands, the dossier,
   an invitation to reply within the period, and an offer to publish the reply next
   to the verdict. Neutral wording, about the claim, never the people.
5. **Send.** The maintainer reviews and sends it from their own account. The
   `reply/` annex records the send date, the SHA-256 of the sealed core, the reply
   deadline and the SHA-256 of the draft. An agent never sends email.
6. **Waiting period (D-15):** 30 days from sending, extendable by up to 14 days by a
   rule defined beforehand, on a justified request. The notice, the deadline and any
   delivery failure are recorded. No reply does not mean agreement.
7. **Reply handling.** The locked verdict never changes. If the authors show an error
   in Refute's procedure, a new claim is written, approved, locked and run; both
   results are published together. Rerun approvals go into a **neutral public
   issue** that holds only the claim id and the SHA-256 of a sealed file with the
   reason and the exact procedure; the file is published with the result (D-16).
   The authors' reply is published only with their permission.

**States recorded for every notice:** "notice sent", "period ended" and "reply
received" are distinct states, each with its date.

### 9.2 Papers with no negative claim (D-14)

- **All claims `REPRODUCED`:** the authors receive a courtesy notice after the seal.
  It **may open an optional reply period**, recorded with the same states. It does
  not delay publication.
- **Only `INCONCLUSIVE` claims, or `INCONCLUSIVE` and `REPRODUCED`, with no negative
  claim:** publication without a mandatory wait, with the same courtesy notice. The
  paper is described as inconclusive for those claims, never as positive or
  reproduced, and stays in the denominators.
- The absence of a wait never waives the gate (section 9.3).

### 9.3 Order: notification, gate, publication (D-17)

1. **Notification:** the notices are sent and recorded.
2. **Gate:** the gate review of the phase. The exit criterion on the right of reply
   is met when at least one notification was sent and recorded, with the send date,
   the SHA-256 of the sealed core and the reply deadline: "the notification was
   made and recorded; the reply period remains open". A courtesy notice that opened
   an optional reply period (section 9.2) is such a notification.
3. **Publication:**
   - a paper with a negative claim is published only after **the gate is passed and
     its reply period, including any extension, has ended**;
   - a paper with no negative claim may be published without waiting for its period,
     but **not before the gate** required by this plan;
   - publication contains the dossier, the verdicts, the authors' reply (if allowed)
     or "authors contacted on <date>, no reply received".

Later replies never change a locked verdict.

## 10. Pre-registration order

### 10.1 Steps

Each step is a separate commit; every step that changes what is locked stops for the
maintainer's approval.

1. **Dependency planning** for v0.3, before any lock, with the 7-day cooldown
   (section 10.5).
2. **Docs:** paper verdict definitions, ML claim spec, sandbox spec, right-of-reply
   procedure, reviewer prompt for paper dossiers.
3. **Acceptance documents, then engine and pack code** with synthetic tests (CI
   offline), work package by work package (section 11). The VM work package (WP6)
   validates the isolation before any third-party code runs.
4. **Pilot protocol** (separate drand round, ordered adjustment list), pilot triage,
   development papers (section 4.5), at most one additional pilot round.
5. **Protocol**: frame snapshot hash, filters, drand round of the papers, the drand
   round reserved for the claims, closed reason lists, thresholds, budget rules,
   attempt limits, tolerances, attack rules and order, minimum coverage: committed
   and pushed before the paper round.
6. **Selection** after the paper round: walk and triage with the maintainer's
   approvals; selection log committed.
7. **Claim inventories** of the 5 papers, with approved transcription, type and
   reference: committed and **pushed** before the claim round.
8. **Claim draw** after the claim round; drawn claims committed.
9. **Lock** of all 5 papers' claims (clean tree), commit, push.
10. **Run** (started by the maintainer), **seal** of the experimental cores, push the
    seal.
11. **Independent reviews** (section 10.3), as annexes.
12. **Notification**, then the **gate review**, then **publication** under section
    9.3.

### 10.2 Dossier verification and experimental reproduction

Two different checks:

- **(a) Dossier verification:** the hashes are checked, the execution states and the
  reasons of every interruption are checked, and the verdicts are recomputed from the
  recorded outputs, without running the experiments again.
- **(b) Experimental reproduction:** the experiments are run again.

For the main sample, a "deterministic verdict" means that (a) recomputes an
identical claim profile. The real rerun (b) is required only for the controlled
tests and for the 2 development papers, within their 96 CPU-hours each. The variation
between runs of each paper is covered by the `seeds` attack, where it applies. Any
rerun of a main-sample paper counts against its 384 CPU-hours. (a) shows that the
classification is deterministic, not that the experiment is repeatable.

### 10.3 Independent reviewers (D-20)

The reviewer protocol of v0.2 (`docs/reviewer-protocol.md`) is adapted to papers:
the reviewer also checks the claim inventory and transcription against the paper and
the triage rejections. A reviewer raises objections; it never sets a verdict. Its
report is an annex of the dossier (section 9.1).

A second reviewer from another model family reviews every dossier with a negative
claim verdict, plus 1 drawn dossier with no negative claim, if access is available
at no additional cost.

### 10.4 Main sample; no additional papers in v0.3 (D-19)

- The main sample is the first 5 **eligible** papers in walk order, under rules fixed
  before any result.
- A paper admitted to the main sample is never replaced because it ended
  `INCONCLUSIVE`, used up its budget or did not reproduce.
- **Additional papers are not planned in v0.3.** A later run of additional papers
  needs a recorded decision of the maintainer and follows the fixed selection rule;
  its results stay separate and never replace the 5 main papers.
- Results over the 5 papers are descriptive and exploratory, restricted to the
  frame, with the named denominators of section 4.4.

### 10.5 Dependency planning (items recorded now)

- `pyarrow` for the Parquet frame, in the `calibration` dependency group, with the
  7-day cooldown (D-18).
- **Python patch versions vary between systems in CI.** The run of 2026-10-14 on the

  `windows-2025`, and 3.13.16 against 3.13.15. Evaluate making uv prefer

- **CI runner image.** The runner OS labels are pinned (`ubuntu-24.04`,

- The Docker Engine version inside the VM is recorded in every dossier; the 7-day

## 12. Risks

| Risk | Mitigation |
|---|---|
| Cherry-picking through triage or claim choice | Closed reason lists, drand order, claim inventories frozen and published before their own drand round, every decision logged with evidence, reviewer audits rejections and inventories, rejection profile published |
| Untrusted code harms the host or the local network | Hyper-V VM; network blocks enforced on the host side; build egress only through an allowlist; containers with no network at run time; no mounts or credentials; maintainer starts every run; all of it validated by WP6 before use |
| Long walk because most papers need a GPU | Pilot with an ordered adjustment list, frame limited to two categories, rejection rate reported |
| Unfair `NOT_REPRODUCIBLE` caused by Refute's limits | Attribution rule of section 8.2 at every stage; undetermined causes are `INCONCLUSIVE` |
| A valid negative conclusion erased by missing work | Verdict order of section 8.1; gates of the base separate from attack prerequisites |
| One expensive claim uses the whole budget | Common setup account, per-claim reserves, frozen attack pool, fixed claim order |
| Harm to authors' reputation | Claim-level verdicts, profile instead of a single label, neutral templates, right of reply, sealed results |
| Leaking a negative result early | Embargo with only hashes or neutral metadata in public; publication only after the gate and the period |
| The sealed package changes after the notice | Immutable experimental core; annexes with their own manifests |
| Tolerances chosen to favor an outcome | Defaults and comparison modes fixed here; per-claim mode and overrides only before the lock, with a reason |
| Nondeterminism (threads, BLAS) | Thread counts fixed in the container; seeds attack; dossier verification recomputes verdicts from recorded outputs; experimental repeatability not claimed for the main sample |
| Code rot in old repositories | Pinned commit, dated dependency resolution, bias declared |
| Licenses of code, data and weights | References, versions and hashes; local copies only when allowed |
| CI environment drift | Pinned runner OS labels; image, Python and dependency versions recorded in every run |
| The VM cannot be built | The phase pauses for the maintainer's decision; nothing is contracted |
