# v0.5.4, first half: the design of I1 and I4 (frozen before their data are read)

**The maintainer's decision of 2026-11-12, 14:00 (#217), item 3.** I1 and then I4 run exactly as
[`v0.5.3-after-round3-decision.md`](v0.5.3-after-round3-decision.md) describes them. Each rule below
is frozen in this document, which is committed and reviewed by Codex before any of its records is
read. Codex also reviews the code before each run, and the exact procedure is posted on #217 before
the run. `method_status: not_validated`. Development data only.

**Nothing here changes `src/`, a battery, a target, or a test rule.** The scripts import Refute and
B1's version 5 (`docs/validation/v0.5.3/stageB/battery_b1.py`, `b1_forecast.py`), all unchanged,
and observe what they produce.

  modelled on stage B's. One line, `v054`, of 50 CPU-h; the first half is a 25 CPU-h sub-line
  (parts `h1_*`).

  - `h1_i1` 8.0 CPU-h;
  - `h1_i4` 8.0;
  - `h1_reserve` 8.9;
  - `h2_unallocated` 25.0.
- **Binding the ledger:** stage B's modules (`b1_forecast` imports `ledger_b`) bind the shared
  `budgeted` to stage B's ledger. So a v0.5.4 script imports them first and `ledger_i` last.
  `ledger_i.assert_bound()` then checks the ledger path, the line, the hard maximum and the save
  function before every mutation. Stage B's records are read by stage B's own readers, with
  `budgeted` pointed at stage B's ledger for that read only, and with saving disabled.
- **The other caps** (`docs/validation/v0.5.4/caps.json`):
  - review tokens: the first half 2.0 M, the phase 3.5 M, counted as in stage B (Codex's events
    under `.cache/v054/codex/`, named `h1-<name>-r<round>-events.jsonl`). An ordinary independent
    review session counts in its scope. The phase's final independent review has its own allowance
    of 0.35 M, recorded apart (`final_review_tokens`) and stopped at 80 % of it;
  - agent-days: the first half 4, the phase 10;
  - disk: 5 GB under `.cache/v054/`. Each run reserves a bound on its output before dispatch
    (its rows times a record bound, plus the driver's files) and checks the disk again after.
- **A STOP at 80 %** of any token cap. Every run checks the caps first.
- **The machine:** processors 8 to 31, BelowNormal, batches of up to 30 minutes, resumable. At most
  10 workers in business hours (the driver's own rule), and 12 otherwise.

## I1. What the records cannot tell

### The populations (from committed records only)

- **T2a:** the 169 losses of configuration B whose decisive blockers include `systematics`
  (`b1-blockers-decisive.json`; the records of B1.4's parts `b1_t2a_2to4` and `b1_t2a_5to20`).
  Each is identified by its key and slot.
- **D2:** the 37 eligible planets that version 5 loses (the completed part's 200 records,
  `b1_d2d4_rest.complete_records`).

### What each rerun does

**T2a.** It rebuilds the injection exactly as `b1_b14.t2a_one` does:
- the same cache, task, draw and injection;
- the same v0.4 search for the candidate.

It runs v0.4's attack as B1 did, and v0.4 must reproduce its C2 record (`c2.compat_problems`,
B1's check). Then it runs **only configuration B's attack**, with version 5's frozen composition
(`b1-composition.json`), as `t2a_one` builds it:
- **at most 4 sectors:** plan `v4A`;
- **5 to 20 sectors:** plan `v4C`, with the selector's refusal lifted.

A spy on `paired.attack_candidate`, the same one `forecast_t2a._outcome` uses, keeps the raw
`systematics` `TestResult`: its status, message, metrics (`sub_checks_run`, `sub_checks_not_run`,
`sub_checks_not_applicable`) and every sensitivity block (`dumps`, `sap`, `background`: detectable,
probability, required probability, effect, alternative). It also keeps the final, enforced test of
every decisive blocker, with its message, and version 5's counters.

**D2.** It rebuilds each planet exactly as `b1_b14.d2_one` does (`c1.generate("P",
development_seed("P", i))`, the same detrend, pre-whitening and search). Then it runs **only
version 5's attack**, with the same spy, and keeps the raw and the enforced `odd_even` and
`sinusoid` results (message, metrics and sensitivity blocks), plus every decisive test's status.

### The reproduction check, before any classification

A rerun **reproduces** its B1 record if all of these hold:
- **T2a:** v0.4's compatibility with its C2 record; the sector count; version 5's final candidate,
  equal to v0.4's (B1's check) and to the record's; the stage verdict; every test's status in the
  brief's `tests`; the brief's `decisive` and `deferred` lists.
- **D2:** the verdict `v5` and every test's status in `v5_tests`.

The inputs are pinned by the fingerprint: the code hash; version 5's code and configuration;
B1.4's scripts and composition; the C2 records and fetch record, B1's fetch report and v0.4's
inputs that `c2.tasks_for` reads (as `b1_b14.fingerprint`); the design; and the rows.

A rerun that does not reproduce is not classified. It is listed, and **the run stops for the
maintainer** (the maintainer's item 5). A rerun that raises an error is a class (iii) case.

### The class table (frozen)

Each held loss is classified **per blocking test**: for T2a, `systematics`; for D2, `odd_even` and
`sinusoid` where they block.

The class comes from the reproduced raw result, replayed through the complete pipeline: the coverage
rule (`enforce_coverage`), then the sensitivity rule (`enforce_sensitivity` with
`registry_for(plan)`), then the stage's deferral. Each intermediate result is kept. The rows are
checked in this order:

| Class | When | Outcome |
|---|---|---|
| **(iii) code defect** | the rerun raised an error; or a block that the result supplies is invalid (`block_problem` is not None), "not applicable" blocks included; or the replayed status differs from the enforced status the attack produced; or a probability is not finite. A block missing because its sub-check did not run is not a defect | **STOP** for the maintainer |
| **(ii) refusal or procedure** | the raw result is INCONCLUSIVE; or it is a PASS turned INCONCLUSIVE by the coverage rule (`enforce_coverage`: no positive coverage); or it is a PASS refused for a reason that is not "insufficient sensitivity" (no sensitivity declared, no applicable sub-check). For `systematics`: a sub-check in `sub_checks_not_run` (A0 refused, outside the grid, no transit measured, error not measurable, not enough data). For `odd_even` and `sinusoid`: their own INCONCLUSIVE classes other than "insufficient_sensitivity" | **route** (a procedure or a domain to fix) |
| **(i) sensitivity** | the raw result is a PASS, and the enforcement refuses it for "insufficient sensitivity" | passed to I2 (T2a) and I4 (D2) as their population |

- **For every class-(i) `systematics` loss**, the record lists **every** non-detectable
  statistical sub-check (`sap`, `background`: the rule blocks with `detectable` and a
  probability), not only the first that `_refusal` names. `dumps` is a categorical block (a
  fraction, with no probability), recorded but never "non-detectable".
- **I2's population** is the class-(i) T2a losses whose `background` block is non-detectable.
- A loss that fits no row (for example a raw FAIL in a held loss) is **unresolved** and listed.
  Nothing is dropped.

### What I1 reports

- **The class table**, with counts per stratum (2 to 4, 5 to 20) for T2a and per test for D2, and
  the non-detectable sub-checks of the class-(i) `systematics` losses (alone and in combination).
- **For class (i) of each test:** the distribution of its blocks' probabilities, and the
  alternative against the required 0.95.
- **For class (ii):** the not-run reasons.
- **For E4 and E2:** whether they operated in each case, read from the counters.
- **I1 decides nothing about targets.** Its only outcomes are route (class (ii)), I2's population
  (class (i) with `background` non-detectable), unresolved, or a STOP (class (iii), or a rerun that
  does not reproduce). D2's class-(i) cases are a diagnostic subgroup for I4's report. **I4's L is
  counted over all 178 eligible planets**, not over this subgroup.

### Its price

B1.4 measured about 64 CPU-s per T2a record of 2 to 4 sectors and about 288 of 5 to 20, for three
batteries. Two batteries here (v0.4 and B) give about 104 × 43 plus 65 × 192 CPU-s. The 37 D2
planets take about 50 each. That is **about 5 CPU-h, 3 to 8 with the uncertainty**, within the 8
allocated to `h1_i1`.

## I4. D2: `odd_even`'s bound with the transit shape as a nuisance parameter

### The populations

- **The 178 eligible fresh planets** of the completed part. **L is counted here.**
- **v0.5.2's 112 eligible planets** (seeds P 1000 to 1119, `forecast_v4`), reported only for
  comparison with stage A's known-template bound.

### What it computes per planet

1. **The planet** is rebuilt as in I1. Version 5's attack runs to obtain its final candidate, and
   the verdict must reproduce B1's record. On the 112, it is version 4's attack against
   `forecast_v4`'s record, as stage A did. A rerun that does not reproduce stops the run for the
   maintainer.
2. **The generator's truth** (`period_days`, `t0_btjd`, `duration_days`, `ingress_fraction`,
   `depth`, the trend, `sigma_white_ppm`, `correlated`) and its covariance: white noise plus each
   sector's exponential term, `σ_r = σ_w / 2` when correlated. This is stage A's
   `odd_even_bound`'s model, unchanged.
3. **The mean model, frozen:** `μ = trend × (1 − d_odd · q_odd − d_even · q_even) + sector
   levels`. `q` is `synthetic.trapezoid`'s unit shape on the odd or even epochs, and the
   derivatives are evaluated at `d_odd = d_even` = the true depth. **The columns of X:**
   - `∂μ/∂d_odd` and `∂μ/∂d_even`: minus the trend times the odd or even unit shape;
   - **the nuisance:** `∂μ/∂θ` for θ in `t0`, `period`, `duration` and `ingress_fraction`,
     **analytic**. On the ramps (0 < shape < 1), with `dt` the trapezoid's own phase offset,
     `n = (t − t0 − dt) / P` the epoch and `w = ingress_fraction × duration`:
     - `∂shape/∂t0 = sign(dt) / w`;
     - `∂shape/∂P = n · sign(dt) / w`;
     - `∂shape/∂duration = |dt| / (ingress_fraction · duration²)`;
     - `∂shape/∂ingress_fraction = −shape / ingress_fraction`;
     - 0 on the plateau and outside;

     each times `−trend × depth`;
   - one constant level per sector.

   No common-depth column is added. The generator's trapezoid has no limb darkening, so there is
   no limb-darkening column.
   - **A convergence check, frozen:** each analytic column is compared with a central difference.
     The steps are 10⁻⁶ day for `t0`, 10⁻⁶ relative for `duration` and `ingress_fraction`, and
     10⁻⁷ day divided by the largest |n| for `period`, so that no transit center moves by more
     than 10⁻⁷ day. A relative L2 difference above 10⁻² puts the planet in E. The step is never
     chosen after L is seen.
4. **The bound:** `F = Xᵀ Σ⁻¹ X` by stage A's polarization of v0.5.1's `mahalanobis2` (k² calls for
   k columns). With the depths first, `S = F_dd − F_dn F_nn⁻¹ F_nd` is the Schur complement of the
   nuisance block. The variance is `(1, −1) S⁻¹ (1, −1)ᵀ = cᵀ F⁻¹ c`, with `c = (1, −1, 0, …)`, and
   `σ_oe` is its square root.
5. **The power:** `gaussian_probability(alternative, σ_oe, max_sigma)` at the battery's own
   alternative: `odd_even_alternative_depth_fraction` times the final candidate's depth, with the
   plan's `odd_even.max_sigma`. This is stage A's function, unchanged.
6. **Stage A's known-template σ,** without the nuisance columns, is kept beside it, as a check:
   adding columns cannot lower σ.

### The rule (frozen)

- **L** counts the 178 eligible planets whose power at the nuisance bound is below 0.95.
- **E** counts the planets whose computation is invalid. They never enter L. An unexpected error or
  an oversized record is not counted in E: it is a binding stop (Codex's round 3, the conservative
  option).
  - `F` with a non-finite entry;
  - `F` not positive definite (its Cholesky factorization fails);
  - `F` ill-conditioned: a condition number above 10¹² after scaling each column to unit diagonal;
  - a non-positive variance, or a non-finite σ or power;
  - the convergence check failed;
  - the nuisance σ below the known-template σ by more than a relative 10⁻⁶.

| Outcome | When |
|---|---|
| **Draft infeasibility of D2** (a non-delegated stop: the run stops for the maintainer) | L ≥ 23. Then at most 155 are kept, against the 156 needed, with every other blocker counted as recoverable |
| **Unresolved** | L < 23 ≤ L + E |
| **Route** | L + E < 23. The gap between version 5's `odd_even` error and the bound is reported as the estimator's target |

**Kept apart, never in L:** the sinusoid's oracle residual at stage A's bound, recomputed on the
178. It is a warning test, which stage A treats as recoverable for kept retention, so it is reported
for a qualified PASS only.

**Conditions:** the Cramér-Rao bound for unbiased estimators; the generator's covariance and its
trapezoid shape family; no limb darkening. It is not a bound for every estimator on real data.

### Its price

The 178 + 112 planets with one battery attack each: about 4 CPU-h at B1.4's measured costs. The
Fisher matrices come on top, at k² `mahalanobis2` calls for k = 6 + the number of sectors columns,
plus the known-template and sinusoid matrices, each cheap (one banded solve per sector). That is
**4 to 8 CPU-h**, within the 8 allocated to `h1_i4`, under the binding budget stop.

This is above the decision page's estimate of 0.5 to 2. The difference is the attack each planet
needs for its final candidate's depth, which the battery's alternative uses. Disclosed here, before
the run.

## The order and the stops

1. Codex reviews this design and the ledger, in up to 3 rounds.
2. The scripts are written: `docs/validation/v0.5.4/i1_diagnose.py` and `i4_bound.py`. Codex
   reviews them in up to 3 rounds.
3. Each script's procedure is posted on #217, then it runs: I1 first, then I4.

**Stops for the maintainer:**
- a class (iii);
- a rerun that does not reproduce;
- I4's draft infeasibility;
- 80 % of a token cap, or any cap reached.

**How a stop binds:**
- The first worker that finds a stop (an error, a class (iii), an oversized record, or a rerun that
  does not reproduce) writes a stop file in its check's output folder.
- Every later shard skips its work and records "SKIPPED".
- `summarize` writes its report and then exits with a failing status, naming the stop. If the
  driver's assembly is refused, the report is written from the verified shards, with the rest
  unknown, and the exit fails. Nothing is reconciled or resumed to get the report. I4's draft is
  found at its `summarize` and stops it the same way.
- **I4 runs only after I1's verified, stop-free result.** The report must match I1's current
  fingerprint and its completed part, with every shard verified, and cover all 206 cases with none
  skipped. No stop may exist in the report, the ledger or I1's stop file. This is checked before
  I4's scheduling, and the report's SHA-256 enters I4's fingerprint.
- *[The tie-break after three Codex rounds (`h1-design`), recorded: these are round 3's conservative
  options, as Codex stated them.]*

**The records stay bounded:** a record above half its reserved bound is replaced by a short
diagnostic and raises a stop. The sinusoid's diagnostic in I4 is isolated, so its failure never
touches a planet's odd/even result.

At the end of the first half, the stop report.
