## 1. Goal and what success means

Make the TESS battery (a) say INCONCLUSIVE when a test could not have detected its declared
minimum effect, and (b) refute the spurious-signal families the pilot exposed (noise and single
events, stellar variability, one-sector centroid artifacts, unstable depth), and **measure**,
with a method fixed before the measurement, how the change moves spurious survival, planet
survival and the INCONCLUSIVE fraction.

The phase **completes with acceptance** when the exit criteria (section 5) hold with evidence:
the measurement is done as pre-registered and reported, pass or fail, like the self-claims of
v0.1 and v0.2. A good number is never a condition of closing. The phase **terminates without
acceptance** when a hard cap is reached before the required evidence exists (section 7).

Synthetic acceptance does not establish validity on real data. The real-data measurements (C2,
C3) cannot validate the method in general either: `method_status` stays `not_validated`.

## 3. What each test must show

Every new or changed test has an acceptance section, committed before its tests and code, with:

1. **What it detects** and what it does not; the limits go into the report.
2. **Its sensitivity rule**, specific to the test (not one formula for all):
   - the effect, the rejection region, the uncertainty model and the minimum detectable effect,
     declared before code;
   - an analytic or a deterministic, simulation-based sensitivity calculation. For a scalar
     estimator with approximately Gaussian error and a one-sided threshold, "detectable when
     `delta_min / sigma >= z_threshold + z_power`" is acceptable within that model; chi-square
     heterogeneity, ratios, two-dimensional offsets and maxima need their own rule;
   - for a check that is not a statistical test (for example a catalog cross-match), an
     explicit, justified applicability category instead of a sensitivity.
3. **Synthetic cases with known truth**, must pass and must fail, in white and correlated noise,
   with gaps, few events, unequal errors and boundary values; **coexistence cases** (a real
   transit together with variability, an edge, a grazing shape, a dilution change between
   sectors, unequal event coverage), so that a stronger test does not refute a real transit for
   its nuisance.
4. **Sensitivity cases:** the effect at the declared minimum with errors small enough that the
   rule says "detectable" (the test FAILs at least at the declared rate, binomial band fixed
   before); errors too large (INCONCLUSIVE, never PASS); no effect and detectable (PASS at the
   declared false-failure rate, binomial band); the reported error calibrated (pulls).
   Injections enter before detrending.
5. **INCONCLUSIVE paths:** zero coverage, too few events, insufficient sensitivity, missing input.
6. **Sabotage checks** (a reduced form of #13): a patched version without the sensitivity rule, or
   without the per-sector qualification, makes a named case fail.
7. **Seeds:** development seeds while building; the acceptance runs on **unseen seeds** declared in
   the acceptance document before code.
8. **Regression:** historical claims (v0.1 to v0.4) give their recorded verdicts and outputs byte
   for byte with the v0.5 code; their resolved claim hashes do not change (#30). New fields and
   tests exist only in a v0.5 claim schema. This does not make the current source hash
   compatible with old locks: old locks still verify at their own tags.
9. **Integration:** with the aggregation rules unchanged, a warning test that returns INCONCLUSIVE
   makes the verdict INCONCLUSIVE (`verdict.py`, rule 3). Extending the sensitivity rule to the
   warning tests is therefore a material change; an integration case shows it, and C1 to C3
   report the INCONCLUSIVE fraction apart.

10. **Severity policy.** Fatal means that the declared signal claim is refuted, not that its
    astrophysical cause is identified. A nuisance found alone (variability, edge proximity, a
    secondary) never becomes fatal by itself:

| Test | Severity | Condition for fatal |
|---|---|---|
| `single_event` | fatal | within its declared multi-event domain (outside it: INCONCLUSIVE) |
| `event_consistency` | fatal | for a declared common-depth model, with calibrated errors and the dilution of each sector applied |
| `edge_events` | warning | fatal only if an accepted test shows that the signal depends on the edge events; too little data left without them: INCONCLUSIVE |
| two-sided phase-0.5 check | warning | never fatal in v0.5: a depth ratio alone does not show incompatibility with a planet while the occultation model is deferred (#181); the v0.4 fatal rule stays only in the historical compatibility path; the check does not cover eccentric secondaries away from phase 0.5 and alone cannot classify an eclipsing binary |
| sinusoid | warning | never fatal in v0.5: a box that is not detected after subtracting the sinusoid is a non-detection, not evidence that variability explains the signal; a joint model comparison is deferred (#182) |
| duty-cycle bound | fatal | only for a geometry the bound excludes (with the stellar parameters' uncertainty); a heuristic search-domain bound is a warning |
| `transit_shape` | warning | never fatal (grazing planets can be V-shaped) |
| `depth_stability` | warning | fatal only if the dilution-corrected depths and their errors pass their acceptance and the common-depth rejection is accepted |
| per-sector centroid | fatal | only with qualified, consistent offsets from at least two sectors; otherwise INCONCLUSIVE |

A test whose code meets its specification but whose scientific acceptance fails (sensitivity or
rates outside the declared bands) is **recorded as FAIL** and enters the battery only as a
diagnostic, never as a decisive test; no second method in this phase. That is a reported result,
not a reason to stop the phase. This applies only to individual scientific tests: a failure of
the **engine's enforcement** (the sensitivity rule, the coverage rule), of **historical
compatibility**, of **input authentication** or of the **reproduction infrastructure** can never
be downgraded; until it is fixed, the phase cannot complete with acceptance.

## 4. Calibration (pre-registered)

Three measurements. Each compares the v0.4 battery and the v0.5 battery **on the same curves and
the same candidates**. The scientific targets, sample sizes, replacement rules and corrupted-run
handling are fixed in the calibration protocol (stop S2), with their rationale and attainable
precision; the C1 design below is frozen now, in the acceptance documents, before any
development result can influence it ([v0.5-acceptance.md](v0.5-acceptance.md), section C1:
scenario distributions, sample-size rule, decision rules).

**Shared reporting rules.** Per battery and per case: REFUTED, WEAKENED, INCONCLUSIVE and SURVIVED
counted separately (survival is never a merged count), and the paired transitions between the two
batteries (a discordance table). Curves, transformations and injections that share a star are not
independent: the star is the cluster unit, and no pooled interval is presented as a coverage
statement. Zero denominators are reported as such.

**How the pairing is done.** The search, detrending, prewhitening and candidate identity are frozen
and run once per curve; both batteries attack the same candidate. This needs a split of candidate
generation from battery evaluation (the current chain does both, `discover/measure.py`). "The v0.4
battery" is a compatibility implementation (the v0.4 claim's tests and parameters run by the v0.5
code), verified per curve against the historical records (candidate, statuses, emitted
severities, stage survival) wherever per-curve records exist, and by counts where only counts
exist. If any upstream step changes, an end-to-end comparison is reported apart.

**C1. Synthetic population study.** Scenarios with known truth: planets (SNR ladder, durations,
one to four sectors); eclipsing binaries at P and 2P with secondaries; sinusoidal and
multi-periodic variability, alone and with a real transit; single-event systematics; edge ramps;
white and red noise only; a pixel-level off-target source and a one-sector pixel artifact.
Metrics per scenario and battery: the four verdict counts, planet survival, kill rate per
false-positive family, noise-only survival, INCONCLUSIVE fraction, with Wilson 95 % intervals.
Development seeds while building; the **confirmation set** has seeds derived from a future drand
round declared in the protocol and runs **once, on frozen code**; only it counts.

**C2. Real data, paired, light-curve tests** (the stage-1 tests of v0.4 plus the new light-curve
tests), on the v0.4 funnel's 100 stars: a **reused benchmark**, not an independent confirmation
(these stars' failures shaped the new tests).
- Input hashes are checked directly against the v0.4 records after a fresh download.
- **Transformed curves:** the 300 transformed curves (1 inverted and 2 per-sector rotations per
  star), regenerated deterministically from the v0.4 protocol's seeds. Inverted and rotated
  curves are reported apart, and so are signal-bearing and original-gate-negative hosts. Neither
  transformation is a validated null (Codex and the literature: LEO-Vetter dropped inversion for
  TESS, Kunimoto et al. 2025, section V.4).
- **Injections:** the v0.4 grid (20 per curve) on the 87 original-gate-negative curves (not
  known signal-free stars). Two numbers per battery: survival among recovered, gate-passing
  injections (the conditional cost) and recovery-and-survival among all attempted injections
  (end to end).
- **Two summaries:** all 100 stars (the historical comparison; 17 of 64 on record) and the
  prespecified analysis subset that excludes the development cases (the three promoted stars of
  v0.4). The historical 17 of 64 is never used as the baseline of the subset; the subset's v0.4
  baseline is measured by the compatibility implementation.
- A new analysis under a new claim, not a rerun of v0.4; its approval is still recorded in an
  issue before it runs.

**C3. Real controls, full battery (stage 2), newly drawn.** Confirmed planets and known false
positives by class (eclipsing binary, off-target, variability where an authoritative disposition
exists), with source and retrieval date, excluding every target of v0.1 to v0.4 (development
targets included). The full signal-identity check runs before any disposition is scored. Its
size is fixed in the protocol within the caps; a sample of about 8 + 8 is a feasibility sample,
not a class-wise validation.

## 5. Exit criteria

1. Every new or changed test has its acceptance section committed before its tests and code, with
   the cases of section 3; the cases run, counts from a JUnit XML file; each test is either
   accepted (decisive) or recorded as failed (diagnostic only).
2. No synthetic test that passes at the start of v0.5 fails at its end without a justification
   written before; historical claims give their recorded verdicts and hashes.
3. Every fatal and warning test of the v0.5 battery declares its sensitivity rule or its
   applicability category, and a PASS without the declared sensitivity is impossible (engine
   rule, shown by a sabotage case).
4. C1's confirmation set run once on frozen code and reported, with every metric, pass or fail.
5. C2 and C3 locked (protocol, code, dependencies, claim), run and reported by the shared
   reporting rules, pass or fail; reviewer reports for the C3 dossiers drawn for review by the
   protocol's rule.
6. Reproduction: one C3 dossier reproduced in a clean clone from the generated instructions
   alone, nothing placed by hand, with identical data hashes and `key_values` equal within
   1e-6; the empty-checkout test runs in CI.
7. Every scope issue closed, or kept open with the part left (section 2), or moved with its
   reason; no `.cache/test-*` folder remains after the suite.
8. Gate: an independent review returns SURVIVED, or WEAKENED with its issues open.

**Allocations** (agent-days): WP0 1.5; WP1 3; WP2 2.5; WP3 2.5; WP4 2; WP6 1.5; WP7 1 (of which
the #188 study at most 0.5 and 2 processor-hours); WP8 1.5; calibration reserve (protocol,

reviewer tokens. Core implementation 15.5, core total 20.5. Optional: WP5 1.5, WP9 1. All
development (WP1 to WP9, the #188 study included) has **at most 50 processor-hours**. The
calibration reserve is an allocation inside the hard caps, not permission to overrun them.

**Reserve invariant.** Before every WP starts, and whenever a WP passes its allocation, the
remaining budget (agent-days and processor-hours) must still cover the untouched calibration
reserve. If it does not, implementation stops: the reduced scope is recorded (what is accepted
stays; what is not is dropped from the decisive set), or, if required infrastructure is not
accepted, the phase terminates without acceptance.

**Stop rule (against the v0.2.1 failure mode):**
1. Each WP gets one acceptance section and at most one revision after Codex's review, before
   its code. After that, bounded repairs may make the code meet its frozen specification; the
   method and the thresholds never change to rescue a result.
2. A WP that exceeds its allocation by 50 % stops, subject to the reserve invariant: what is
   accepted stays; what is not is recorded and dropped from the decisive set (a scientific test)
   or blocks acceptance (required infrastructure, section 3).
3. **Scope reduction trigger:** at 12 agent-days used or on 2026-12-01, whichever comes first,
   every optional WP not started is dropped and the remaining core work is reassessed against the
   reserve invariant. The calibration starts only after the required infrastructure is accepted
   and the battery under test is frozen.
4. If C1's confirmation or any declared target fails: no rerun, no retuning; the maintainer
   records a decision.
5. At any hard cap, a terminal report: if required evidence is incomplete, the phase ends
   **without acceptance**; no extension and no new preliminary study.
6. A divergence with Codex that persists after three rounds goes to the maintainer with both
   arguments.

## 9a. Decisions at S2 (the maintainer, 2026-11-03)

   fail. The per-sector centroid is an item for a future phase (#200).
5. **Row 1.10 in white noise** is recorded only (the decided window lies 0.67 day after a segment

6. The roles of the v0.5 battery are those of the acceptance README: `single_event` and

## 9b. The deviation at S4 (the maintainer, 2026-11-04)

The claim written by the frozen code could not be loaded (its targets attachment carried two
fields the TESS schema refuses), and the frozen C3 steps neither placed the TESS-EB edition in
their cache nor checked the claim against its lock. The maintainer kept the original draw (round
6612465) under a narrow, recorded deviation (#199; `calibration/v0.5/deviation/README.md`):
original code and selection kept; claim packaging and input preparation under a deviation
approved on 2026-11-04. Exit criterion 6 is not waived.

**Lesson:** before a freeze, exercise the claim packaging end to end with synthetic targets
(write the claim with the code to be frozen, load it, lock it and run each step on synthetic
data), so that a schema or input-placement defect is found before the code is frozen.
